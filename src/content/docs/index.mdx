## Install

Pick your package manager. The package ships the native addon as a per-platform
optional dependency, so there is no Rust toolchain and no build step on your side.

<Tabs>
  <TabItem label="npm">
    ```sh
    npm install @sendust/ts
    ```
  </TabItem>
  <TabItem label="pnpm">
    ```sh
    pnpm add @sendust/ts
    ```
  </TabItem>
  <TabItem label="yarn">
    ```sh
    yarn add @sendust/ts
    ```
  </TabItem>
  <TabItem label="bun">
    ```sh
    bun add @sendust/ts
    ```
  </TabItem>
</Tabs>

Deno resolves the same package through npm compatibility; its required flags are
in the [quick start](guide/quick-start/).

## Why Rust

The SMTP engine, MIME composition and validation are Rust, compiled per platform
and reached through one Node-API bridge — no worker process, no JavaScript sitting
between your call and the socket. The [architecture overview](architecture/overview/)
covers the two crates, the runtime-neutral facade, and where each responsibility sits.

## What the engine does for you

<CardGrid>
  <Card title="Queue and pool">
    Concurrent `send()` calls are accepted and scheduled: up to `delivery.maxConcurrent`
    at once over at most `delivery.maxConnections` native sessions, one SMTP
    transaction per session. The queue is bounded, so a full queue is
    `LIMIT_QUEUE_FULL` rather than unbounded memory.
  </Card>
  <Card title="Sessions stay warm">
    A definitive outcome resets the session and keeps it — up to
    `delivery.maxMessagesPerSession` messages or `delivery.sessionIdleMs` of idleness.
    An error or an `unknown` disposition drops it, so reuse can never duplicate a send.
  </Card>
  <Card title="Acceptance, not delivery">
    `accepted` means the relay took responsibility. There is no `delivered`,
    `opened` or `bounced` status, and the library never retries `unknown` on its own.
  </Card>
</CardGrid>
